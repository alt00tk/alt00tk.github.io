# ローカルIssueを管理する

## 運用契約を読み込む

作業前に`references/issue-workflow.md`を最後まで読む。
この文書は、このスキルの人間向け運用とCLI契約の正本である。
状態規則を再記述したり、独自に解釈したりしない。

一覧表示、検証、初期化、すべての状態遷移には`node .agents/skills/manage-local-issues/scripts/issues.js`を使う。
Issueのスキーマには`templates/issue.md`だけを使う。
CLIは現在のリポジトリにある`docs/issues`を操作する。
索引ファイルを作成したり、Issue作成機能をスクリプトへ追加したりしない。

プロジェクトは`docs/issues/config.json`に`id_prefix`という一つのフィールドを持たなければならない。
この接頭辞はプロジェクトのIssue識別子の名前空間を定めるが、運用契約は変更しない。

## 作業を選ぶ

会話の文脈だけに依存する前に、現在の一覧を生成する。

- 現在の依頼に一致するactive Issueがあれば、その作業を続ける。
- 無関係なIssueがactiveの場合は、黙って一時停止や置き換えを行わず、競合を報告して指示を求める。
- active Issueがない場合は、意図が依頼に明確に一致するdraftだけを選ぶ。
- 複数のIssueが候補になる場合は、ユーザーに選択を求め、優先順位を作ったり推測したりしない。
- 一致するIssueがない場合は、draft Issueの候補を提示し、`references/issue-workflow.md`に従ってユーザーが明示的に承諾した後にテンプレートから作成する。
Issue IDを再利用しない。

ユーザーが次に推奨するIssueを求めた場合は、すべてのdraftの順位付けを求めずに一つを推奨する。
推奨は、現在のIssue一覧とIssue本文を次の基準で判断する。

- 阻害解消：依存するIssueの着手を可能にする作業や、繰り返している不確実性を解消する作業を優先する。
- 設計適合：互換経路を増やさず、単純で長期的に維持できる境界を強める作業を優先する。
- 範囲管理：隣接する作業を取り込まず、本文の意図を完了できるIssueを優先する。
- 検証確度：自動確認または手動確認の方法が明確なIssueを優先する。
- ユーザーの意図：他のIssueに一般的な価値があっても、直前にユーザーが指定したテーマを優先する。

推薦理由では、判断に影響した基準を説明する。
目的が異なる近い候補があれば示す。
永続的な優先順位を保存したり、暗黙に示したりしない。

## 範囲を管理する

選択したIssueを実装ファイルの編集前にactiveへ移動する。
Issue本文と依存関係を最後まで読む。

実装ファイルを編集する前に、`references/issue-workflow.md`のブランチ規則に従い、Issue IDを含むIssueブランチを作成するか、そのブランチへ切り替える。
現在のブランチがactive Issueと一致しない場合は、先にブランチを修正する。
ユーザーがIssueについて明示的に上書きしない限り、Issue作業で`main`を直接編集しない。

Issueに記載された意図と受け入れ条件だけを実装する。
独立した価値を持つ作業が見つかった場合は、現在のIssueへ取り込まず、別のdraft Issue候補として提示し、ユーザーが明示的に承諾した後に作成する。
現在の実装を通すためだけに受け入れ条件を弱めたり書き換えたりしない。

Issueの品質境界の外にある作業を、受け入れ条件、不変条件、実在する経路、既知の障害、外部契約の根拠なしに、作業を阻害するレビュー指摘やactive Issueの範囲へ追加しない。
価値のある隣接作業にこのような根拠がある場合も、現在の受け入れ条件が明示的に拡張を要求しない限り、別のdraft Issue候補として提示し、ユーザーが明示的に承諾した後に作成する。

active Issueが文書化された設計や操作方法を変更する場合に限り、関連文書を同じ変更へ含める。

Issueの状態遷移は`draft`→`active`→`closed`だけを許可する。
`active`には実装、コミット、レビュー、修正、マージ承諾待ちを含める。
着手後に`draft`へ戻したり、`closed`を再オープンしたりしない。
完了後に追加作業が必要になった場合は、新しいIssueのdraft候補を提示し、ユーザーが明示的に承諾した後に起案する。
draft Issueを実装せず撤回する場合は、元の問題、意図、受け入れ条件を「当初の提案（未実装）」へ保存し、撤回後の本文に現在の受け入れ条件と検証記録を記載する。
元の未実装条件を完了扱いにせず、通常の`draft`→`active`→`closed`を通す。

## 標準実装ループ

1. active Issue、依存Issue、Issueが直接関係するファイルを読む。
2. 小さな変更でない場合は、具体的な実装計画を示す。
3. active Issueの範囲だけを編集する。
4. 意味のある最小の確認を先に実行し、その後に変更が要求する広い確認を実行する。
5. ユーザーが手動確認の内容を尋ねた場合は、変更した振る舞い、受け入れ条件、想定される失敗経路から確認項目を作る。
   内部のコード読解を手順へ含めず、ユーザーが実行できる確認にする。
6. 受け入れ条件のチェックボックスは、証拠を得た後にだけ更新する。

active Issueでレビュー指摘を受けた場合は、編集前に各指摘を分類する。

- 範囲内：記載された意図または受け入れ条件へ直接影響する場合は、active Issueで修正する。
- 範囲外だが価値がある：別のdraft Issue候補として提示し、ユーザーが明示的に承諾した後に作成して、active Issueの範囲を保つ。
- 対応不要：変更せずに、その理由を説明する。

レビューのたびに、`references/issue-workflow.md`で定めた粒度でIssueの`レビュー指摘`を更新する。
同じ根本原因の指摘をまとめ、対応判断と証拠を記録する。
レビュー記録の転記ではなく、必要な後続Issue候補またはプロジェクトで定めた再発防止記録の行き先を示す。
承諾されていない候補を実在するIssueとして扱わず、後続Issueはユーザーが明示的に承諾した後に作成する。

## 作業を完了する

すべての受け入れ条件を確認してからチェックボックスを更新する。
`完了記録`に正確な変更、検証結果、レビュー観点を記録してから、スクリプトでIssueをclosedへ移動する。

マージ承諾前はIssueを`active`に留める。
承諾後はIssueブランチ上でIssueを`closed`へ移動し、その変更をコミットしてから、`main`へ`--no-ff`でマージする。

GitHub PRはこの運用に含めない。
`完了記録`をローカルPRの記録として扱う。
Issueブランチをmainへマージできる状態として報告する前に、`references/issue-workflow.md`のローカルレビューコマンドを検討または実行する。
標準の統合経路は`main`への`--no-ff`マージであり、squash mergeではない。

`main`へマージしたり`origin/main`へpushしたりする前に、現在の会話で人間へ明示的な許可を求める。
ユーザーがコミットを許可していても、これをマージやpushの許可とは扱わない。

許可を得た後は、次の順序で統合する。

1. ブランチ、作業ツリー、active Issueの状態、`main`との差分、マージ対象のcommitを確認する。
2. `node .agents/skills/manage-local-issues/scripts/issues.js list`を含む、関連する検証コマンドを実行する。
3. `main`へ切り替え、`--no-ff`でマージし、`origin main`へpushする。
4. `main...origin/main`、active Issueの件数、最終検証結果を確認してから完了を報告する。

一部成功を完了として報告しない。
ブロックされた場合は理由を記録したうえでIssueを`active`に留める。
巻き戻しや再オープンで状態を回避しない。
