# 日英同時公開と本文の記事間リンクをビルドで検査する

## 問題

日英ファイルの欠落や本文の参照先・言語の誤りを人の確認だけに任せると、日英同時公開の契約が破られ得る。

## 意図

日英ペアと記事間リンクの契約に違反した公開物の生成をビルドで止める。

## 受け入れ条件

- [ ] npm run buildで全記事の日英slug集合の一致を検査し、どちらか片方しかない場合はビルドを非0で終了する。公開日時の不一致もエラーにする。
- [ ] 本文の記事間リンクは日本語/articles/{slug}/、英語/en/articles/{slug}/のサイト内絶対パスに統一し、同じ言語の実在する記事を参照していることを検査する。
- [ ] 通常形式と参照形式のMarkdownリンクを構文として解析する。コード内のリンク例を参照と誤判定しない。相対形式および同一サイトの完全URLによる記事参照も検知し、規定形式へ修正するよう報告する。
- [ ] テンプレートが生成する言語切替・英語注釈の原文リンクは意図的な言語間参照として有効にする。外部サイトへのリンクと記事以外の参照を記事間リンクとして誤判定しない。
- [ ] クエリ・フラグメント付き記事リンクでも記事の存在と言語を検査し、それらの有無で検査を回避できない。見出しIDの存在確認は行わない。
- [ ] エラーには原因ファイル、対象slugまたはリンク先、違反理由を示す。欠落、日時不一致、リンク切れ、言語違い、形式違反を識別できる。
- [ ] 日英欠落の両方向、リンクの各形式と正常・異常経路、コード例、外部リンクを検証し、正常な日英記事一式は既存の公開CIでビルドできる。
- [ ] 日英同時公開、記事間リンク形式、原文更新時の日英確認、翻訳・レビュー後に同じ変更で公開する手順を関連する運用文書に記載する。

## 対象外

- 外部リンクのHTTP到達確認
- 見出しフラグメントの存在検証
- 本文リンクの自動修正
- 訳の意味やレビュー実施の自動判定
- 原文変更時の翻訳鮮度をハッシュで強制する仕組み

## 品質境界

ビルド入力全体の日英ペア、公開日時および本文の記事参照を契約として守る。同時公開は同じ配備成果物に両言語を含む意味とし、翻訳内容の妥当性は執筆・ChatGPTレビュー工程で担保する。

## 実装メモ

正規表現だけのMarkdown抽出を避け、実際のMarkdown解析・出力経路でリンクを扱う方法を検討する。導入前提は既存記事の日英対応が完了していること。mainへこの強制検査を早期導入しない。失敗時は前の配備を維持し、契約を満たす原稿へ修正する。ロールバックする場合は検査解除が公開契約を弱める点を記録する。

- このJP/EN対応では、一時的な `develop` を統合先とする。Issueブランチは最新の `develop` から作成し、Issue IDを含める。各Issueは承認後にclosedの記録を含めて `develop` へ `--no-ff` で統合する。通常運用のmain向け統合規則に対する、今回のユーザー承認済み例外である。
- mainでは日本語記事の執筆・公開を続ける。必要時および最終統合前にmainをdevelopへ取り込み、記事を失わない。Issueの完了はdevelopへの統合を意味し、本番配備済みとは扱わない。
- BLOG-021〜BLOG-024がすべてclosedとなり、最新mainを取り込んだ全記事の日英対応とビルドを再確認してから、人間の明示承認を得てdevelopをmainへ `--no-ff` で統合する。承認済みなのは今回の起案内容のmainへの直接コミットまでで、将来の統合・push承認を含まない。
- 本Issueは依存と記載の前提が満たされれば後続Issueなしでビルド・配備できる状態にする。実際の本番公開は全Issue完了後とし、main向けの既存配備workflowは維持する。
