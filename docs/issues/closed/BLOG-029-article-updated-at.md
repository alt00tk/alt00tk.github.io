# 記事詳細に日英共通の更新日を表示する

## 問題

記事のfrontmatterには初回公開日時しかなく、読者は実質的な改訂がいつ公開されたかを記事詳細から確認できない。

## 意図

日英ペアで公開した最後の実質的な改訂日時を、初回公開日と区別して読者に示す。

## 受け入れ条件

- [x] 日英両方に同じ `updatedAt` を指定すると、日英の記事詳細で初回公開日の右隣に更新アイコンと更新日が表示される。横幅が足りない場合は更新日を次の行に表示し、未指定時は初回公開日だけを表示する。公開Markdownにも原稿の値が反映される。
- [x] 日英片側だけの指定、値の不一致、タイムゾーンなし、初回公開と同時刻またはそれ以前の指定で静的ビルドが失敗し、対象原稿と理由を特定できる。
- [x] 一覧とRSSは初回公開日時順を保ち、RSSの `pubDate` は初回公開日時を示す。
- [x] 公開手順に記録基準と日英同時指定の例があり、既存の公開契約テストと日英回帰検証が通る。独立レビュー結果を記録する。

## 対象外

- 更新通知、改訂履歴、過去の更新日時の補完、一覧・OGP・RSS・llms.txtへの更新日時の追加。

## 品質境界

日英ペアを単位とする単一の契約を全原稿に適用する。日時の前後はオフセットとミリ秒未満を考慮して時刻として判定し、日英の値は表記までそろえる。

## 実装メモ

公開契約、共通の記事詳細、既存の日時比較・整形、日英の生成物を確認する。

## 設計判断

- 日英ペアが共有する一つの改訂日時を、両原稿に明記する。省略は改訂日時の記録がない状態を表す。Gitの更新日時には翻訳の追加や体裁修正も含まれるため、改訂の記録は公開時の著者の判断に委ねる。
- 初回公開日時順と改訂日時の前後判定は、同じ日時比較処理を使う。表示は共通の記事詳細に置き、公開Markdownには原稿から反映する。
- 更新アイコンと更新日は一組で配置する。長い英語ラベルも一般的なモバイル幅に収まるよう、狭い画面で更新日を併記する場合は日付を小さくする。

## レビュー指摘

- 長い小数秒を `Date` で解釈するとミリ秒を誤る場合があり、公開前の `updatedAt` がビルドを通過した。ミリ秒より下の桁を切ってから `Date` に渡し、前後判定には元の下位桁を使う。反例を公開契約テストに加え、独立レビューでは別実装を基準にした10,000組の時刻比較と一覧ソートでも一致を確認した。
- 一覧は検索用に全記事のリンクを持つため、リンクの有無で一覧ページの掲載を判定するテストが失敗した。記事行の `hidden` 属性で日英それぞれの1ページ目と2ページ目を確認するよう修正し、日英回帰テストで確認した。
- 独立再レビューで両指摘の解消を確認した。横並びへの変更では、日英実記事の横並びと折り返し、日時の意味、未更新時の表示を独立検証した。残存指摘なし。

## 完了記録

- 変更は `updatedAt` の入力と日英公開契約、記事詳細での表示、公開手順と回帰検証。現行原稿の日時は履歴から補完せず、公開済み原稿の編集は不要。
- 検証は `npm run build` で36ページと公開Markdown32件、`node scripts/test-publication-contract.mjs` で26ケース、`node scripts/test-bilingual.mjs` で生成物とChromiumの回帰が通過。独立レビューとIssue一覧の検証、`git diff --check` も実施した。
- 記事詳細の更新日表示がなければHTML検査が失敗し、日英片側指定・同時刻・長い小数秒の反例を拒否する処理がなければ対応するビルド検査が失敗することを実装過程で確認した。
- マージ前のレビュー観点は、日英ペアでの指定の一致、公開と改訂の時刻順、日英記事詳細での表示、一覧とRSSの初回公開日時順。
- 横並びへの変更では、Chromiumで日英の1280 pxと375 pxの横並び、250 pxでの折り返し、ラベルとアイコンを検証した。実記事の一時プレビューでも、1280 pxと375 pxで両言語の横並びを確認した。
